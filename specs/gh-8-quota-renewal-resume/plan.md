# Implementation Plan: Quota-Aware Harness Resume

**Branch**: `symphony/gh-8-quota-renewal-resume` | **Date**: 2026-09-30 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/gh-8-quota-renewal-resume/spec.md`

## Summary

Treat Codex quota exhaustion as a durable scheduler wait rather than a worker failure. The Codex adapter normalizes app-server quota errors into a harness-neutral signal containing a stable, non-secret pool key, validated renewal information, and native thread identity. The existing orchestrator remains the single owner of mutable scheduling state: it releases the worker slot, persists an issue-scoped quota wait through a small filesystem store under the configured workspace root, suppresses dispatch for the exhausted pool, reconciles eligibility on every poll, and resumes the saved Codex thread exactly once when eligible. An unavailable native thread becomes an operator block; Symphony never reconstructs a fresh conversation automatically.

## Technical Context

**Language/Version**: Elixir 1.19 on OTP 28

**Primary Dependencies**: Existing OTP/GenServer orchestration, Ecto embedded configuration schema, Jason JSON encoding, Codex app-server JSON-RPC over stdio, Phoenix status surface

**Storage**: Atomic JSON quota-wait records in a reserved `.symphony/quota-waits/` directory under the configured workspace root; no database and no prompt/provider-payload persistence

**Testing**: ExUnit with real orchestrator processes and deterministic fake Codex/tracker inputs; targeted `mix test` and final `make -C elixir all`

**Target Platform**: Existing local Linux service runtime; remote SSH workers preserve their current workspace placement while durable scheduler metadata remains host-side

**Project Type**: Long-running Elixir orchestration service with Codex app-server integration and HTTP/terminal status surfaces

**Performance Goals**: A renewed eligible wait becomes dispatchable within one polling interval plus 5 seconds; repeated polls perform no duplicate resume; persistence/recovery work is linear in the number of quota-paused issues and does not consume agent slots

**Constraints**: One authoritative scheduler owner; idempotent restart/reconciliation transitions; no credentials, prompts, model outputs, or raw provider responses in state/logs; native thread resume is mandatory; normal concurrency and routing remain authoritative; public functions require `@spec`

**Scale/Scope**: Codex end-to-end in this issue, with a small harness-neutral signal/reference contract and no Claude or GitHub Copilot adapter; tens of concurrent issue runs and quota waits per service instance, bounded by existing concurrency configuration

**Structure Decision**: Extend the existing single Elixir application. `Harness.Quota` is a pure normalization contract, `QuotaWaitStore` owns validated atomic serialization only, Codex owns provider-specific signal parsing and thread resume, and `Orchestrator` alone owns lifecycle and scheduling transitions. Existing presenter/dashboard modules expose the new state without creating a parallel control plane.

## Design Phases

### Phase 0 — Research

Resolve Codex app-server quota signal shapes and `thread/resume` behavior, select the durable-state boundary, define pool suppression semantics, and compare unknown-renewal policies. Decisions and rejected alternatives are recorded in [research.md](research.md).

### Phase 1 — Domain and contracts

Define quota-pool, quota-wait, continuation-reference, and resume-dispatch states with explicit validation and transitions in [data-model.md](data-model.md). Define the adapter result and resume contract in [harness-quota-resume.md](contracts/harness-quota-resume.md), the persisted allowlist in [quota-wait-state.schema.json](contracts/quota-wait-state.schema.json), and executable validation scenarios in [quickstart.md](quickstart.md).

### Phase 2 — Task planning (after plan approval)

Generate TDD-first tasks organized by the three user stories. The first slice classifies and persists quota waiting; the second restores and resumes native context idempotently; the third adds status, lifecycle recovery, and documentation. Each coherent slice runs focused tests before the full gate.
