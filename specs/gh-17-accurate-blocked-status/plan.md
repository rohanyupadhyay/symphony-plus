# Implementation Plan: Accurate Blocked Session Status

**Branch**: `symphony-plus/gh-17-accurate-blocked-status` | **Date**: 2026-10-12 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/gh-17-accurate-blocked-status/spec.md`

## Summary

Introduce one pure runtime-status projection boundary that classifies each issue exactly once before any terminal, JSON, or LiveView rendering. The projection gives operator-blocked conditions precedence over recoverable quota waits, preserves quota diagnostic context when quota recovery requires intervention, sanitizes displayed reasons, and derives lists and counts from the same classified entries. The orchestrator remains the sole owner of mutable scheduling state; this feature changes only its read projection and the existing observability renderers.

## Technical Context

**Language/Version**: Elixir 1.19 on OTP 28

**Primary Dependencies**: Existing OTP/GenServer orchestrator, Phoenix LiveView, shared web presenter, terminal status dashboard, PubSub refresh path

**Storage**: Existing in-memory orchestrator state and durable quota-wait JSON records; no new persistence

**Testing**: ExUnit with pure projection tests plus real orchestrator/status-surface tests; targeted `mix test` and final `make -C elixir all`

**Target Platform**: Existing long-running Linux/macOS Symphony Plus service

**Project Type**: Elixir/OTP service with terminal, HTTP JSON, and Phoenix LiveView observability surfaces

**Performance Goals**: Classification remains linear in the number of runtime records; one completed snapshot updates all counts and rows through the existing PubSub cycle

**Constraints**: One primary classification per issue; orchestrator remains the only mutable state owner; no raw provider payloads or secrets; no new persistence or operator command; public functions require adjacent `@spec`

**Scale/Scope**: Tens of concurrent running, retrying, blocked, and quota-paused issues per service instance; changes limited to runtime projection, existing renderers, focused docs, and tests

**Structure Decision**: Extend the existing single Elixir application. `RuntimeStatus` is a pure read-model boundary that accepts the orchestrator's current runtime collections, applies one documented precedence rule, and returns the lists and counts consumed by every status surface. `Orchestrator` retains exclusive ownership of mutable lifecycle state; `Presenter`, `StatusDashboard`, and `DashboardLive` only serialize or render the normalized snapshot.

## Design Phases

### Phase 0 — Research

Confirm the current source of duplication and display drift, select the classification boundary and precedence, define safe reason handling, and determine regression boundaries. Decisions and rejected alternatives are recorded in [research.md](research.md).

### Phase 1 — Domain and contracts

Define runtime records, normalized status entries, classification invariants, and lifecycle transitions in [data-model.md](data-model.md). Define the terminal/JSON/LiveView projection contract in [runtime-status-projection.md](contracts/runtime-status-projection.md) and executable validation scenarios in [quickstart.md](quickstart.md).

### Phase 2 — Task planning (after plan approval)

Generate TDD-first tasks by user story: unique primary classification and diagnostics first, trustworthy counts and renderers second, then transition/restart coverage and documentation. Each coherent slice runs focused tests before the full gate.
